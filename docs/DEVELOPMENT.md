# 만들면서 바뀐 것들

기능 목록보다 어떤 불편을 해결하려 했는지 남기기 위한 기록입니다. 지금까지의 작업은 한 번에 완성한 설계가 아니라, 사용하면서 발견한 문제를 수정한 결과입니다. 아래 내용은 현재 소스와 검증 기록을 바탕으로 나중에 정리한 회고입니다. 당시 커밋이 있었던 것처럼 이력을 만들지는 않았습니다.

## 기록이 귀찮으면 기록 도구도 안 쓰게 된다

시작과 정지를 매번 누르는 방식은 시작만 누르고 정지를 잊기 쉬웠습니다. 휴대폰에서는 점수를 숫자로 입력하려고 키보드가 올라오면 정작 시간표가 가려졌습니다.

목표를 ‘정확하게 타이머를 누르기’보다 ‘지나간 행동을 적은 조작으로 남기기’로 잡았습니다. 빈칸을 드래그하고 잠시 누르면 카테고리를 고른 뒤 바로 집중·만족도를 입력할 수 있게 했습니다. 이미 카테고리가 있는 칸은 점수 선택부터 엽니다. 점수 하나를 눌렀다고 메뉴를 닫지 않아 연속 입력할 수 있게 했습니다.

블록 양끝으로 길이를 조절하고, 되돌리기 버튼으로 입력을 취소할 수 있게 했습니다. 계획과 실제의 색조를 구분하고, 계획 칸과 상단 영역의 높이를 줄여 한 화면에서 읽을 수 있는 시간을 늘렸습니다.

코드: [`mobile/mobile.js`](../mobile/mobile.js), [`mobile/mobile.css`](../mobile/mobile.css)

## 계획은 바뀌어도 과거까지 바뀌면 안 된다

늦게 먹은 식사를 입력하자 그 식사의 원래 계획까지 움직이는 문제가 있었습니다. 이렇게 되면 원래 무엇을 하려고 했는지와 실제로 무엇을 했는지가 구분되지 않습니다.

실제 기록은 사실로 보존하고, 과거·현재에 해당하는 계획은 고정한 뒤 이후 행동만 다시 계산하도록 바꿨습니다. 집중도와 만족도 외에 ‘계획한 때에 시작하고 마쳤는가’를 보는 이행도도 추가했습니다. 이행도는 자동 조정 후의 계획에 소급해서 맞추지 않고, 해당 행동을 기록하기 전 비교 기준을 보관합니다. 식사는 빨리 먹었다고 불이익이 생기지 않도록 시작 시각만 평가합니다.

코드: [`source/PlanHistory.cs`](../source/PlanHistory.cs), [`source/Adherence.cs`](../source/Adherence.cs), [`mobile/offline-core.js`](../mobile/offline-core.js)

## 취침 목표와 조건 충족 시각은 다른 값이다

4끼니가 늦어지면 수면 예상도 같이 늦어졌습니다. 취침을 고정하고 버퍼를 쓰려는 목적과 맞지 않았습니다. 확인해 보니 식후 휴식까지 확보되는 시각을 수면 표시에도 사용하고 있었습니다.

화면에 표시하는 취침은 기상 기준의 원래 목표로 고정했습니다. 식사 간격과 식후 휴식, 남은 행동까지 조건을 만족시키는 데 필요한 시각은 내부에서 따로 계산합니다. 그 차이를 기준으로 대기 시간과 선택 활동을 순서대로 줄입니다.

실제 4끼니를 너무 늦게 먹어 ‘식후 2시간 휴식’과 취침 목표를 동시에 지킬 수 없다면 이미 한 행동을 지우거나 목표를 밀어서 해결한 것처럼 보이지 않게 했습니다. 취침과 기록은 유지하고 부족한 시간을 표시합니다.

검증에서는 늦은 식사 입력 후에도 취침 표시·소등 구간·수면 알림·만족도 평균의 종료 시각이 유지되는지 확인했습니다.

코드: [`source/Adaptive.cs`](../source/Adaptive.cs), [`mobile/fixed-sleep-tests.cjs`](../mobile/fixed-sleep-tests.cjs)

## 휴대폰은 PC가 없어도 완전히 동작해야 한다

초기 구조에서는 PC가 일정 계산을 담당했습니다. PC와 연결되지 않으면 기록은 남겨도 자동 계획 조정과 카테고리 관리가 제한됐습니다. 휴대폰을 주로 쓰려는 방식과 맞지 않았습니다.

휴대폰에도 로컬 상태와 일정 엔진을 두어 오프라인에서 계산하게 했습니다. PC와 다시 연결되면 변경을 비교해 합치고, 같은 영역을 양쪽에서 바꿔 자동으로 결정할 수 없으면 양쪽 기록을 보관한 뒤 사용자가 고르게 했습니다. C#과 JavaScript 두 엔진의 결과가 달라지는 것을 확인하기 위해 같은 시나리오를 비교했습니다.

노션 저장도 PC를 거치는 대신 휴대폰에서 직접 처리합니다. 전송할 기록은 기기에 보관하고 실패하면 재시도합니다. 날짜는 자정이 아닌 기상일에 귀속시키며, 기상 외 기록이 없는 날은 일기를 만들지 않습니다.

코드: [`source/ReplicaSync.cs`](../source/ReplicaSync.cs), [`mobile/offline-core.js`](../mobile/offline-core.js), [`android/src/ara/daily/NotionDiarySync.java`](../android/src/ara/daily/NotionDiarySync.java)

## 인터넷이 되는데 ‘인터넷 연결 확인’이 나왔다

10월 20일 기록이 노션에 없었고, 휴대폰에는 HTTP 400과 인터넷을 확인하라는 문구가 나왔습니다. 코드가 여러 HTTP 오류를 하나의 인터넷 오류로 바꾸고 있어 로그인 갱신 실패와 노션 요청 오류를 구분할 수 없었습니다.

Android 2.7에서 인증 갱신·접근 권한·요청 거절·서버 오류를 나눴습니다. 서버가 세션 만료를 명시한 경우에는 새 세션을 만들고 한 번만 다시 요청합니다. 일반 400이나 결과가 불명확한 통신 실패에 생성 요청을 무조건 반복하지 않습니다. 재로그인도 기록과 저장 위치를 유지한 채 할 수 있도록 바꿨습니다.

오류 화면에 인증 정보가 섞이지 않도록 원문 응답 대신 허용한 오류 코드만 보여줍니다. 모의 HTTP 응답을 실제 Android 통신 클래스에 넣어 세션 복구, 재시도 횟수 제한, 일반 400의 재전송 방지를 확인했습니다.

다만 휴대폰의 기존 오류 응답 원문에는 접근하지 못했습니다. 따라서 당시 400의 정확한 원인이 인증 갱신인지 세션 만료인지는 아직 확정하지 않았습니다. 2.7 설치 후 실제 기록이 노션에 반영되는지도 추가 확인이 필요합니다.

코드: [`android/src/ara/daily/NotionHub.java`](../android/src/ara/daily/NotionHub.java), [`android/src/ara/daily/NotionFailure.java`](../android/src/ara/daily/NotionFailure.java)

## 식사 준비를 기록했는데 ‘이른 끼니’ 오류가 났다

2끼니를 일찍 먹은 뒤, 존2와 식사 사이의 빈 실제 칸에 ‘2끼니 준비’를 끌어다 놓으면 입력이 막혔다. 같은 순서로 재현해 보니, 일찍 먹은 식사에 맞춰 앞 계획을 줄이는 과정에서 새 준비 기록을 그 앞 활동을 실제로 했다는 증거로 잘못 판단하고 있었다.

준비는 준비 기록으로 남기되, 앞 활동의 실행 여부를 판단하는 검사에서는 제외했다. 다른 실제 활동의 충돌 검사는 유지했다. 준비를 복사하거나 카테고리로 입력한 뒤에도 기존 기록과 위 계획이 바뀌지 않는지 검사했다. 회귀 검사는 모바일 10가지와 PC 2개를 추가했고, PC 전체 243개와 PC·모바일 계산 비교 907건을 통과했다.

코드: [`source/Routine.cs`](../source/Routine.cs), [`mobile/prep-record-tests.cjs`](../mobile/prep-record-tests.cjs)

## 만족도가 계속 2점 근처에 머물렀다

하루 중간에 기록을 보는데 만족도가 자꾸 2점에 가까웠다. 아직 오지 않은 저녁 시간까지 빈칸 2점으로 평균에 들어가고 있었다. 기상부터 현재까지만 계산하고, 지난 날은 수면 예상 시각에서 끝내도록 바꿨다. 빈칸을 어떤 점수로 볼지도 사람마다 다를 수 있어 기본 점수를 0~5점으로 고르거나 빈칸을 평균에서 제외할 수 있게 했다. 이미 기록한 점수는 바꾸지 않는다.

새벽에 일어났는데 기본 기상 시각 때문에 시간표가 07시부터 보이는 문제도 있었다. 기상 확정 여부를 따로 저장해 확정 전에는 00시부터 표시하고, 기상을 고른 뒤에는 그 위 한 시간부터 표시하게 했다.

시간이 흐르면서 평균만 바뀐 것을 기록 수정으로 판단하지 않도록 동기화 비교값에서는 시간에 따라 달라지는 집계값을 제외했다. 계산·저장·동기화 회귀 검사와 브라우저에서 03시 기상 및 빈칸 점수 선택을 확인했다.

코드: [`source/SatisfactionPolicy.cs`](../source/SatisfactionPolicy.cs), [`mobile/satisfaction-tests.cjs`](../mobile/satisfaction-tests.cjs)

## 10분 때문에 3끼니를 빼고 있었다

앞쪽 대기 버퍼를 다 쓴 뒤 10분만 더 조정하면 되는 경우에도 3끼니가 빠졌다. 식사를 빼기 전에 요거트와 취침 사이의 여유를 먼저 쓰도록 순서를 바꿨다.

새 단계에서는 요거트를 다 먹은 뒤 취침까지 최소 30분을 남긴다. 기본 계획의 요거트는 10분이고 원래 종료 후 여유가 50분이라 최대 20분을 쓸 수 있다. 부족한 시간이 10분이면 10분만 사용한다. 이것으로 맞춰지면 3끼니를 유지하고, 그래도 부족하면 기존 3끼니 제외 단계로 넘어간다.

기본 루틴의 첫 식사가 70·80분 늦어진 검사에서는 3끼니를 유지했고, 90분 지연에서는 새 버퍼를 먼저 쓴 뒤 3끼니를 제외했다. 취침 목표와 실제 기록은 유지했다. 이후 단계에서 요거트 간격을 추가 완화하거나 요거트를 제외하는 기존 동작은 그대로다.

## 앞으로 남길 기록

패치마다 긴 글을 쓰기보다 아래 네 가지만 짧게 남기려 합니다.

1. 실제로 불편하거나 잘못된 동작
2. 해결하려는 목표
3. 바꾼 방식과 선택한 이유
4. 확인한 결과와 아직 확인하지 못한 부분

## 체크리스트를 시간 기록과 연결

할 일을 보고 기록하려고 매번 카테고리 메뉴를 여는 게 번거로웠다. 목록을 옆에 열어 두고 실제 칸으로 끌어 기록하도록 바꿨다. 끄는 도중 지나친 칸까지 기록되면 의도한 시간보다 길어져서, 기본은 도착한 칸만 기록하고 잠시 멈춘 뒤에만 범위를 늘리게 했다.

시간을 기록했다고 할 일이 끝난 것은 아니다. 기록에는 할 일 ID를 넣고, 완료는 기존 날짜별 체크 상태를 공유하도록 했다. 점수를 바꾸며 블록이 나뉘거나 PC와 병합해도 ID가 남는다. 이름과 카테고리가 같아도 서로 다른 할 일은 합치지 않는다. 기록 삭제와 할 일 삭제도 각각 상대방의 기록을 지우지 않는다.

## 노션 갱신이 거절된 뒤의 재시도

휴대폰에서 인증 거절 400이 반복됐다. 앱은 재연결 필요 표시를 저장했지만 다음 요청에서 그 표시를 확인하지 않았고, 연결 상태도 토큰 문자열이 남아 있는지만 보고 있었다.

갱신이 거절되면 인증 정보 사용과 예약 전송을 중단하고 재연결 상태를 유지하게 했다. 기록과 저장 위치는 보존한다. 정상적인 만료 갱신과 서버 일시 오류는 따로 검사했다. 최초 거절의 구체적인 원인과 실제 휴대폰의 재연결 성공은 아직 확인하지 못했다.

## 새 로그인 오류를 이전 오류가 가린 문제

2.8로 재연결해도 400이 나왔다. 앱의 상태 표시가 재연결 필요 플래그를 우선하면서 새 로그인 실패 메시지 대신 이전 갱신 거절을 보여 주는 문제가 있었다. 최신 결과를 우선하고, 브라우저에도 단계와 제한된 오류 코드를 표시하게 했다. 실제 휴대폰에서의 원인 확정과 로그인 성공은 아직 남아 있다.
